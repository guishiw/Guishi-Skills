# 项目蒸馏器

把成熟项目蒸馏成可运行的“项目认知框架”。目标不是复述目录或技术栈，而是让后续 Agent 能回答：请求如何流动、状态在哪里改变、边界为什么这样划分、如何安全扩展，以及哪些设计只在特定条件下成立。

## 交付目标

默认生成独立 Skill：`<project-name>-framework/`，用于指导后续 Agent 理解、诊断、修改或迁移该项目，同时保留证据坐标和不确定性。

最终 Skill 至少包含：项目使命和核心闭环、运行时拓扑和入口、模块职责与依赖方向、3–7 个架构原则、关键调用链、数据与状态生命周期、扩展规则、工程护栏、诚实边界和源码证据索引。

不要把文件树、框架名称或 README 摘要冒充“项目框架”。

## 入口分流

| 用户目标 | 默认产物 |
|---|---|
| 理解项目 | 架构地图 + 调用链 + 项目框架 Skill |
| 接手维护 | 上述内容 + 变更指南 + 风险热点 |
| 迁移/重构 | 上述内容 + 可迁移原则与项目特有约束的分离 |
| 复刻同类产品 | 上述内容 + 能力骨架；不复制受限制实现 |
| 更新已有项目 Skill | 增量核对代码变化，只刷新受影响部分 |

用户未限定时按“理解并接手维护”执行。只在仓库范围、访问权限或产物选择会实质改变结果时追问；其余使用默认值推进。

## Phase 0：范围和基线

1. 定位仓库根目录，读取适用的 `AGENTS.md`、贡献说明和本地规则。
2. 检查 Git 状态、当前分支、子模块/工作区结构；不得覆盖用户现有改动。
3. 确认分析范围是单体仓库、某个子系统还是跨仓依赖。
4. 记录当前 commit；无 Git 时记录扫描日期和根路径。
5. 判断项目类型和主要语言，但暂不下架构结论。
6. 可运行 `scripts/inventory_repo.py <repo-root> --output <file>` 生成初步清单；该清单只是导航，不是结论。

创建目标目录：

```text
<project-name>-framework/
├── SKILL.md
└── references/
    ├── 00-scope-and-evidence.md
    ├── 01-system-map.md
    ├── 02-runtime-and-entrypoints.md
    ├── 03-module-boundaries.md
    ├── 04-critical-flows.md
    ├── 05-data-and-state.md
    ├── 06-extension-and-operations.md
    └── 07-decisions-and-evolution.md
```

所有底稿必须位于目标 Skill 内，保证复制目录后仍可独立使用。

## Phase 1：证据驱动的项目解剖

按七个视角调查。可以并行，但每个视角必须落盘；并发不可用时串行完成。

| 文件 | 要回答的问题 |
|---|---|
| `00-scope-and-evidence.md` | 分析了哪些目录、commit 和运行环境？哪些被排除？ |
| `01-system-map.md` | 用户、外部系统、进程、服务和部署单元怎样连接？ |
| `02-runtime-and-entrypoints.md` | 项目怎样启动？真实入口、配置装配和生命周期是什么？ |
| `03-module-boundaries.md` | 模块各自负责什么？允许和禁止的依赖方向是什么？ |
| `04-critical-flows.md` | 3–5 条关键业务/技术链路怎样从入口走到结果？ |
| `05-data-and-state.md` | 核心实体、持久化、缓存、消息、事务和状态转换在哪里？ |
| `06-extension-and-operations.md` | 插件点、配置、测试、构建、发布、观测、失败恢复怎样工作？ |
| `07-decisions-and-evolution.md` | 哪些设计选择反复出现？历史变化、权衡和遗留约束是什么？ |

### 证据顺序

优先追踪真实运行链路：

```text
启动/请求入口 → 路由或调度 → 应用服务 → 领域逻辑
→ 端口/适配器 → 持久化或外部系统 → 结果契约与失败路径
```

README、架构文档和注释是线索，不是最终证据。用源码、配置、测试、迁移、构建文件或可观察运行行为交叉验证。

每条重要结论标记为：`事实`、`推断`、`未知`或`历史`。引用尽量使用 `path:line`、符号名、配置键或测试名，避免只写文件名。

## Phase 1.5：证据检查点

提炼前确认：

- 至少找到一个真实启动入口和一个完整关键链路。
- README 与实现不一致时已显式记录。
- 每个核心模块都有职责、调用者和依赖对象。
- 数据写入、状态转换和失败路径不是空白。
- 对动态注册、反射、代码生成、消息驱动等机制已说明验证方法。

若关键入口或持久化链路仍未知，先补证据，不要开始总结架构原则。

## Phase 2：框架提炼

读取 [references/extraction-framework.md](references/extraction-framework.md)，从底稿中提炼 3–7 个项目框架原则。

每个候选原则必须回答：

1. 是否跨两个以上模块或关键链路复现？
2. 能否预测新功能应该放在哪里、如何连接？
3. 违反它是否会造成可解释的后果？
4. 它是项目特有选择，还是框架默认行为或行业常识？

只有前三项成立、且第四项已被区分时，才提升为“项目框架原则”。否则降级为实现惯例、局部模式或待验证假设。

同时区分不可变内核、稳定边界、可替换机制和偶然复杂度。不要把历史包袱变成推荐实践。

## Phase 2.5：提炼检查点

展示或记录：系统一句话模型、3–7 个原则名称、3 条关键链路、不可变内核与可替换机制、最大证据缺口和风险。用户未要求中途确认时可以继续，但这些内容必须进入交付摘要。

## Phase 3：生成项目框架 Skill

读取 [references/output-template.md](references/output-template.md) 生成目标 `SKILL.md`。入口保持精炼，把大量文件清单、逐链路证据和历史记录留在 `references/`。

目标 Skill 必须提供面向后续任务的执行协议：

1. 判断任务属于定位、修改、扩展、迁移还是故障诊断。
2. 按相关关键链路读取最少必要证据。
3. 明确改动跨越哪些边界和契约。
4. 复用既有扩展点；若需打破原则，先说明原因和影响。
5. 验证真实结果契约，不以“能编译”或“端口已监听”代替业务成功。

禁止生成“永远照此架构实现”的绝对命令。成熟项目中的历史选择可能只适用于当时约束。

## Phase 4：验证

读取 [references/validation-rubric.md](references/validation-rubric.md)，至少执行：

- **回放测试**：用 Skill 解释一条已知链路，核对源码。
- **放置测试**：给出合理新需求，看 Skill 能否预测修改位置和依赖方向。
- **故障测试**：给出典型失败，看 Skill 是否沿真实链路定位。
- **边界测试**：询问未覆盖子系统，结果应标记未知而非编造。

内容验证比标题和关键词计数更重要。失败时回到证据或提炼阶段；最多两轮，仍不确定的部分进入诚实边界。

## 更新模式

1. 读取已有 Skill 的基线 commit 和证据索引。
2. 比较基线与当前版本的文件和符号变化。
3. 找出受影响的入口、链路、数据契约和原则。
4. 只更新受影响的底稿和 Skill section。
5. 重跑相关测试并记录新基线，不无依据重写整个 Skill。

## 安全与边界

- 默认只读分析；“蒸馏”不等于授权修改源项目。
- 不读取或输出密钥、生产数据、个人数据和无关敏感文件。
- 复刻项目时遵守许可证、版权和商标边界；提炼思想不等于复制实现。
- 不把测试、样例或废弃代码自动当作生产架构。
- 不因目录叫 `domain`、`service` 或 `core` 就假定职责；追踪真实调用者。
- 无法访问完整微服务、插件或跨仓依赖时，明确边界，不虚构组件。

## 完成标准

- 目标 Skill 和底稿均在目标目录内。
- 重要结论有源码或运行证据。
- 原则能指导新需求，而不只是解释旧代码。
- 项目特有设计、框架默认和历史包袱已分开。
- 未知项、时效基线和不适用范围清晰。
- 验证包含实际任务，不只做静态格式检查。
