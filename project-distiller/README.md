# Project Distiller

把成熟代码库提炼成可复用、可验证、可持续更新的项目框架 Skill。

Project Distiller 不以目录树或技术栈清单代替架构分析。它从真实入口、关键调用链、数据状态、模块依赖和运行行为出发，提炼一个项目真正稳定的设计原则，并把结果组织成后续 AI Agent 可以直接使用的 Skill。

## 适用场景

当你需要完成以下工作时，可以使用这个 Skill：

- 快速理解一个成熟项目的整体结构和核心业务闭环
- 接手陌生代码库，建立可靠的维护导航
- 追踪请求、任务、事件从入口到最终结果的完整链路
- 提炼模块边界、依赖方向和数据所有权
- 判断新功能应该放在哪一层、连接哪些契约
- 为项目迁移、重构或同类产品设计提取可复用框架
- 将一次项目分析沉淀为可持续更新的项目专属 Skill

以下请求通常会触发它：

```text
帮我蒸馏这个项目的架构
把这个成熟项目做成一个项目框架 Skill
分析这个仓库真正的模块边界和调用链
提取这个项目可复用的工程骨架
我准备接手这个项目，帮我建立维护框架
更新之前生成的项目 Skill
```

它不用于只修复一个 Bug、普通代码审查、生成简单项目介绍或只列出技术栈。

## 核心产物

默认生成一个独立的 `<project-name>-framework/` Skill：

```text
<project-name>-framework/
├── SKILL.md
└── references/
    ├── 00-scope-and-evidence.md
    ├── 01-system-map.md
    ├── 02-runtime-and-entrypoints.md
    ├── 03-module-boundaries.md
    ├── 04-critical-flows.md
    ├── 05-data-and-state.md
    ├── 06-extension-and-operations.md
    └── 07-decisions-and-evolution.md
```

生成结果包含：

- 项目使命、用户角色和核心业务闭环
- 启动路径、运行时拓扑和真实入口
- 模块职责、调用者、依赖对象和禁止依赖方向
- 3–7 个能够指导新需求的架构原则
- 3–5 条关键业务或技术调用链
- 数据所有权、事务、缓存、消息和状态生命周期
- 扩展点、配置机制、测试策略和运行护栏
- 项目特有设计、框架默认行为与历史包袱的区分
- 已验证事实、合理推断、未知项和适用边界
- 可回溯到源码、配置、测试或运行结果的证据索引

## 工作原理

### 1. 建立分析基线

识别仓库根目录、当前 commit、工作区结构、子模块和项目规则。分析默认保持只读，不修改源项目。

### 2. 从真实链路读取项目

优先追踪：

```text
启动或请求入口
  → 路由与调度
  → 应用服务
  → 核心业务逻辑
  → 端口与适配器
  → 数据库或外部系统
  → 结果契约与失败路径
```

README、架构文档和注释只作为导航线索，关键结论需要源码、配置、测试、迁移文件或运行结果交叉验证。

### 3. 从实现中提炼框架原则

一个候选原则需要通过四项检查：

1. 是否在多个模块或关键链路中重复出现？
2. 是否能预测新功能应该放在哪里、如何连接？
3. 违反它是否会产生具体、可解释的后果？
4. 它是项目主动设计，还是底层框架默认行为、外部约束或历史遗留？

只有具备生成力的规则才会上升为项目框架原则。局部实现方式会保留为惯例或证据，不会被包装成普遍架构结论。

### 4. 生成可运行的项目 Skill

最终 Skill 不只描述项目，还会告诉后续 Agent：

- 面对定位、修改、扩展、迁移和故障诊断任务时先读什么
- 应沿哪条调用链继续追踪
- 哪些模块和契约会受到影响
- 应复用哪个现有扩展点
- 如何验证真实业务结果
- 哪些结论超出当前证据范围

### 5. 使用真实任务验证

交付前执行四类验证：

| 测试 | 验证内容 |
|---|---|
| 回放测试 | 能否准确解释一条已知调用链 |
| 放置测试 | 能否为一个新需求预测正确修改位置和依赖方向 |
| 故障测试 | 能否沿项目真实链路诊断典型失败 |
| 边界测试 | 面对未覆盖区域时是否明确标记未知 |

## 使用方法

### 安装

将 `project-distiller` 目录放入 Agent Runtime 对应的 skills 目录。例如：

```text
Codex:      ~/.codex/skills/project-distiller/
Claude Code: ~/.claude/skills/project-distiller/
Cursor:     ~/.cursor/skills/project-distiller/
```

也可以直接在当前工作区中引用本目录。

### 基础使用

```text
使用 $project-distiller 分析 /path/to/repository，生成这个项目的框架 Skill。
```

如果没有额外说明，默认按“理解并接手维护”模式执行。

### 指定分析目标

```text
使用 $project-distiller 分析这个项目，重点提炼插件架构和扩展机制。
```

```text
使用 $project-distiller 分析支付子系统，追踪下单、支付、回调和退款链路。
```

```text
使用 $project-distiller 提取这个项目中可迁移到新系统的架构原则，同时排除历史兼容代码。
```

### 使用本地运行证据

如果项目能够安全启动，可以要求结合测试或最小业务请求验证：

```text
使用 $project-distiller 分析这个仓库，并用现有测试和本地最小请求验证关键调用链。
```

是否启动项目、修改配置或连接外部环境，仍受当前任务授权范围约束。

### 更新已有项目 Skill

```text
使用 $project-distiller 更新 my-project-framework，比较原基线和当前代码，只刷新受影响的链路与原则。
```

更新流程会比较基线版本和当前代码，定位受影响的入口、模块、数据契约和架构原则，不会无依据重写全部内容。

## 仓库盘点工具

项目附带一个轻量仓库清单脚本：

```bash
python3 scripts/inventory_repo.py /path/to/repository
```

将结果保存为文件：

```bash
python3 scripts/inventory_repo.py /path/to/repository \
  --output /tmp/repository-inventory.md
```

限制扫描文件数量：

```bash
python3 scripts/inventory_repo.py /path/to/repository \
  --max-files 10000
```

脚本会列出顶层目录、构建清单、候选入口、配置文件、测试文件和主要代码后缀。它只用于导航，不能替代对真实调用关系的分析。

## 分析原则

### 证据优先

重要结论应尽量带有 `path:line`、符号名、配置键、测试名或运行结果。每条结论区分为：

- `事实`：由代码或运行行为直接证明
- `推断`：由多个事实支持，但项目没有明确声明
- `未知`：当前证据不足
- `历史`：只在旧版本或迁移阶段成立

### 生成力优先

高质量架构原则必须能指导未来任务，而不只是解释现有文件。例如，它应该帮助判断：

- 新功能放在哪个模块
- 哪一层拥有数据和状态
- 哪些依赖方向不能反转
- 哪个扩展点应该复用
- 哪些测试和观测必须补充

### 保留边界

无法访问的微服务、外部平台、动态插件或生产行为必须明确标记。项目框架 Skill 不应虚构缺失组件，也不应把当前快照描述成永久不变的事实。

## 安全边界

- 默认只读分析，不因“分析”或“蒸馏”自动获得代码修改、部署或外部写入权限。
- 不读取或输出密钥、生产数据、个人数据及与架构无关的敏感内容。
- 不把测试样例、废弃代码或演示模块自动当成生产架构。
- 复刻同类项目时遵守源码许可证、版权、商标和数据使用边界。
- 不能用“编译成功”“端口已监听”代替真实业务结果验证。

## 质量标准

一个合格的项目框架 Skill 应满足：

- 能从真实入口解释至少一条完整调用链
- 模块职责和依赖方向有源码证据
- 框架原则能够指导新需求，而非只解释旧代码
- 数据所有权、状态变化和失败路径清晰
- 项目设计与框架默认、外部约束、历史包袱已分离
- 未覆盖范围、推断项和证据基线明确
- 回放、放置、故障和边界测试均有可核对结果

详细执行指令见 [`SKILL.md`](SKILL.md)。
