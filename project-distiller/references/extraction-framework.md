# 项目框架提炼方法

## 从事实到原则

```text
源码/配置/测试/运行结果
  → 多条链路中的重复结构
  → 候选设计规则
  → 用新需求验证其生成力
  → 项目框架原则
```

“使用 Spring”“有 services 目录”“采用 REST”通常只是技术事实，不是项目框架原则。

## 四项验证

### 跨链路复现

原则至少在两个不同模块或业务链路出现。只在一个文件成立的是局部模式。

### 生成力

原则应能预测新功能应放到哪里、经过哪些契约、哪些依赖方向不能反转，以及需要补哪些测试和观测。

### 反事实后果

假设违反原则，应能指出具体后果，例如事务边界破坏、状态双写、租户泄漏、插件失去隔离或升级路径被锁死。

### 来源归因

识别它属于项目主动设计、底层框架默认、法规/组织/部署约束，还是历史遗留。不能确认来源时标为推断。

## 原则记录格式

```markdown
### 原则：名称

- 一句话：
- 证据：至少两个独立场景，含源码坐标
- 生成规则：遇到什么任务时怎样指导放置或连接
- 违反后果：
- 适用范围：
- 例外：
- 置信度：高/中/低
```

## 四层框架

- **业务框架**：用户价值怎样形成闭环；哪些概念和状态是核心。
- **应用框架**：请求、任务、事件怎样编排；事务和权限在哪层处理。
- **技术框架**：模块、端口、适配器、插件和外部系统怎样连接。
- **运行框架**：配置、部署、观测、扩缩容和恢复怎样支撑系统。

不要只提炼技术框架而遗漏业务闭环和运行约束。

## 常见误判

- 把目录树当架构。
- 把框架官方推荐当项目独特设计。
- 从接口定义推断实现，却不追踪实际绑定和调用者。
- 只看成功路径，遗漏重试、补偿、幂等和降级。
- 从当前快照推断长期意图，却不看迁移和提交历史。
- 把偶然复杂度包装成值得复用的模式。

## 项目骨架与项目复制

可以提炼模块角色、契约形状、状态机、扩展点、质量门槛和决策方法。不要默认复制品牌元素、私有算法、受限制数据、未经许可的实现代码或依赖组织内部系统的细节。
