# 项目框架 Skill 验证量表

## 核心测试

### 回放测试

选一条已由源码确认的关键链路，让新 Skill 独立解释。核对入口、调用顺序、状态变化、结果和失败路径。

### 放置测试

构造项目风格一致的新需求，要求说明修改哪些模块、复用哪个扩展点、哪些契约不能破坏、应补哪些测试和观测。答案必须由源码证据支持，而非按目录名猜测。

### 故障测试

构造跨层失败，例如请求成功但未持久化、事件重复消费或配置加载错误。Skill 应给出贴合真实链路的排查顺序和判定证据。

### 边界测试

询问未分析模块、外部服务内部实现或基线之后的行为。Skill 应明确未知，并提出最小验证路径。

## 评分维度

| 维度 | 权重 | 通过标准 |
|---|---:|---|
| 事实准确性 | 30 | 关键链路与源码一致，无虚构组件 |
| 生成力 | 25 | 能指导新需求放置和依赖设计 |
| 边界完整性 | 15 | 区分事实、推断、未知和历史 |
| 证据可追溯 | 15 | 关键结论可定位到源码、配置、测试或运行结果 |
| 可操作性 | 15 | 后续 Agent 能据此行动，而非只读到概述 |

建议 80 分以上交付。低于 80 分时优先补证据和调用链，不要靠增加章节数量提高观感。

## 失败信号

- 只会复述 README 或目录树。
- 新需求永远回答“新增一个 service”。
- 把编译通过、进程存活当成业务验证完成。
- 未知问题仍给出确定答案。
- 给出大量文件名，却无法解释依赖方向和状态所有权。
